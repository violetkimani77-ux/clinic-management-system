## 2026-09-07 — Notifications, dashboard and platform-control boundary

### Queued / clarified on branch
- Branch: `chore/rename-hali-to-heri`.
- Established the product boundary: the clinic **dashboard** answers “what is happening now?”, clinic **notifications** answer “what needs my attention?”, and the Heri **Platform Control** answers “what is happening across Heri itself?”.
- Clinic notifications are not to be generated by the Platform Control UI. They originate from clinic workflow events and are routed by clinic role/permission.
- Clinic admin notifications will focus on important staff-account actions, operational exceptions, important pharmacy/accounts exceptions and security/account events.
- Pharmacy notifications will focus on low stock, expiry, expired stock, dispensing/prescription exceptions and stock discrepancies.
- Accounts notifications will focus on overdue/materially outstanding invoices, payment/reconciliation exceptions, failed/incomplete transactions and billing items requiring review.
- Ordinary live dashboard metrics such as patients today, visits today, revenue today and raw outstanding totals remain dashboard data rather than notifications unless an explicit actionable threshold/event is reached.
- Platform Control notifications are reserved for explicitly authorized Heri platform operators and cover platform events such as tenant provisioning/health, subscription lifecycle, residency/security failures and failed migrations/operations.
- Initial notification delivery is planned as in-app with unread/read state, history, severity, role-aware routing, direct workflow links and deliberate noise controls. Email/SMS/push remain later channel layers.
- Created `docs/HERI-NOTIFICATIONS-AND-CONTROL-BOUNDARIES.md` as the durable design boundary before implementation.

### Code audit findings recorded
- The dashboard already reads live database-backed metrics per request and has an inline “Needs attention” list for pharmacy stock/expiry and accounts outstanding balances. This is useful operational context but is not yet a persistent notification center.
- Pharmacy is substantially established in code: clinic-scoped prescriptions/stock/expiry reads, FEFO dispensing, stock movement, pharmacy billing linkage and audit event are implemented.
- Accounts is substantially established in code: clinic-scoped invoices/payments, invoice creation, payment recording, duplicate external-reference protection, invoice status updates and audit events are implemented.
- Roles already distinguish `ADMIN`, `PHARMACY` and `ACCOUNTS`, with permission-based access and clinic-membership-scoped sessions.
- Repository search did not surface a persistent notification subsystem. Therefore notifications should be built as a new layer rather than duplicating existing dashboard metrics.
- Pharmacy, accounts and user-management workflows still require end-to-end completeness, permissions, edge-case and test audits before they are treated as fully production-ready notification sources.

## Durable operating rules

- Never run production migrations locally; production migrations run through CI with `prisma migrate deploy`.
- Do not modify applied Prisma migrations or use `db push`/`migrate reset` against production.
- Do not expose or log passwords, signup secrets, health data, or other sensitive user data.
- Do not create real clinical records merely to test production readiness.
- Record material changes here with status (`completed`, `verified`, `queued`, or `blocked`) and include commit/PR/deployment/workflow identifiers where available.
